# ADR-0008:雙模式(救援+進水口)與自動化政策

狀態:Accepted(2026-07-14,Metal 訪談定案:「救援 + 長期進水口」、
「人工只審低信心 + 破壞性」、總量 < 5 萬檔)

## 背景

原 roadmap 隱含假設 phoxif 是一次性救援工具。Metal 拍板:歷史存量清完後,
未來新收到的轉存檔仍持續走 phoxif 進水、去重、補值、歸檔。這改變三件事:
catalog 的生命週期、「已處理過」的判定、以及自動化程度的預設值
(長期使用下,逐張人工不可持續)。

## 決策

1. **同一條管線,兩個模式**:rescue(批次 campaign,staging 是複本、
   原始檔不動)與 inbox(指定 intake 資料夾,檔案唯一本就地處理)。
   模式記在 batch 上,不 fork 程式路徑。
2. **Catalog 永久化**:跨 campaign 不重建;「這張照片以前處理過嗎」
   = 查 sha256。**重逢規則**:新目擊的 sha256 已 `archived` → 自動標
   duplicate、源檔進待刪批次;不重新走 enrich。
3. **App 仍是工具型**,不做長駐監看/daemon:開 app 時檢查 intake
   資料夾,有新檔就提示開 batch。
4. **自動化政策矩陣**(唯一authoritative表在 `docs/pipeline-design.md` §10):
   - 寫入型動作(日期/GPS,可逆:有標記 + catalog 原值)→ **自動執行**,
     低信心級距附非阻塞摘要清單。
   - 刪除型動作(dup 輸家進垃圾桶)→ **批次一鍵批准**,不逐張。
   - 近重複灰區(phash 距離 4 < d ≤ 10)與補值落空 → 人工佇列。
   - NAS 寫入 → 逐 plan 批准(全域「動前必問」)。

## 理由

1. 進水口模式的價值主張就是「丟進去、開一下 app、按一次批准」——
   逐張 review 會讓工具被棄用(長期行為現實)。
2. 寫入/刪除的批准粒度差異來自可逆性:寫入有原值可回復(ADR-0004/0006),
   刪除只剩垃圾桶這一層保險——所以刪除保留人工批准,但以批次為粒度
   兼顧安全與可持續。
3. 「同一條管線兩個入口」而非兩套流程:< 5 萬檔量級沒有效能理由分家,
   分家必然漂移(對照 ADR-0007 的兩套 sorter 教訓)。

## 被否決的替代方案

- **純一次性工具**(清完就封存):與 Metal 的實際需求不符——WeChat/LINE
  的轉存檔會持續產生。
- **長駐 daemon / folder watcher**:違背「tool-type app」既有決策
  (memory:open→process→close);對單人工作流,開 app 時掃一次已足夠。
- **全自動含刪除**:誤殺不可再生原檔的風險不對稱;垃圾桶是最後一層,
  不該是唯一一層。
- **逐張 review 一切**(原 GUI 五步流程的隱含模式):首批可以,長期不可持續。

## 重估訊號

- inbox 佇列常態性積壓 > 2 週:批准粒度或佇列設計錯了,重新檢討矩陣。
- 批次批准後的垃圾桶誤殺被實際觸發(從垃圾桶撈檔)≥ 2 次:
  收緊 T_auto 或將 exact-dup 以外的刪除改回逐組批准。
- 出現「需要在來源機器上常駐收集」的需求:重開 daemon 討論,先問 Metal。

## 正例/反例

- ✅ 正例:32 張新 WeChat 轉存丟進 intake → 開 app → batch 自動跑完
  (3 張重逢自動標 dup、29 張補日期含標記)→ 待刪批次畫面列 3 張
  → 一鍵批准 → 關 app。人工互動:一次點擊。
- ❌ 反例:為了「保險」把日期寫入也改成逐張批准——寫入是可逆的,
  這是把人工預算花在錯的極性上(違反本 ADR 的粒度原則)。
