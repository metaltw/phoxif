# ADR-0005:GPS 補齊 = 保守極性,寧缺勿錯

狀態:Accepted(2026-07-07)

## 背景

日期補齊的極性是「盡量填」(ADR-0004),直覺會想把 GPS 也比照辦理。
但兩者的錯誤代價不對稱:日期錯了,timeline 位置偏移,有標記可查可修;
GPS 錯了,照片出現在地圖上一個**具體而可信的錯誤地點**——多年後你會
把它當成事實(「原來這張是在京都拍的」),錯誤會被記憶固化。

## 決策

GPS 只允許兩種寫入來源:

1. **人工斷言的資料夾 → 座標映射**(現 `write_gps.py` 的 `gps_locations`
   機制,未來 GUI 化):人明確說「這個資料夾都是東京」。信心 = 人工。
2. **時間鄰近推斷**,但必須同時滿足全部條件:
   - 目標檔的日期來源是**第 1 或 2 級**(原生 EXIF 或相機命名檔名,
     見 ADR-0004 階梯)——估計日期之上不疊加推斷;
   - 參照檔與目標檔來自**同一來源裝置/同一相機膠卷批次**
     (catalog 的 source 證據判定,不能只看資料夾);
   - 時間差 ≤ 30 分鐘(config 可調,只准調小不准調大);
   - 寫入時加 keywords `phoxif:gps-estimated`、`phoxif:gps-src:temporal-neighbor`,
     catalog 記參照檔 sha256 與時間差。

所有 GPS 補值都寫 `phoxif:gps-backfilled` 與來源標記。人工映射另寫
`phoxif:gps-user-confirmed`;時間鄰近才寫 `phoxif:gps-estimated`。圖片同時
寫 IPTC Keywords + XMP Subject；MP4/MOV 不支援 legacy IPTC IIM，改以
`Keys:GPSCoordinates` + XMP Subject 保存座標與溯源。

**明確禁止**:

- 對 WeChat/LINE 轉存檔(日期為估計者)做任何 GPS 自動推斷。
- 從資料夾**名稱**自動 geocode 寫入(「東京」資料夾 ≠ 每張都在東京;
  只能作為 GUI 中給人確認的**建議值**,人按了確認才走來源 1)。
- 反向 geocode 快取(`.geocache.json`)僅供 organize 分類顯示用,
  不得回寫 EXIF。

落空者:不寫,不標,保持無 GPS。無 GPS 在 Immich 只是不上地圖,無害。

## 理由

1. 錯誤極性不對稱(見背景)。缺 GPS 的照片是誠實的;錯 GPS 的照片是謊言。
2. 轉存檔的收到時間與拍攝地點毫無因果(在台北收到東京拍的照片),
   時間鄰近推斷的前提(時間≈拍攝時間)對它不成立——誤差相乘。
3. 條件全部機器可判定(catalog 查表),弱模型可執行、可測試。

## 被否決的替代方案

- **與日期同極性(盡量填+標記)**:標記擋不住地圖上的視覺說服力,
  錯的定位點會被當真。
- **全自動 geocode(資料夾名/相簿名 → 座標)**:一個混入的檔案就是一個
  永久的錯誤地標。

## 重估訊號

- 若 Immich 端出現「以估計 GPS 分區瀏覽」的強需求且人工映射覆蓋率過低:
  可考慮放寬到「寫入但用專用低信心標記+獨立開關」,先問 Metal。
- 時間鄰近推斷實測誤判率(抽查)>2%:收緊窗口或停用來源 2。

## 正例/反例

- ✅ 正例:IMG_5023.HEIC(原生 EXIF 日期)無 GPS,同機膠卷前後 10 分鐘
  的 IMG_5021/IMG_5027 都有 GPS 且相距 200m → 內插寫入 + estimated 標記。
- ❌ 反例:mmexport 檔的估計日期落在東京行程區間,就近繼承東京座標——
  它可能是朋友傳來的台北聚餐照。禁止。
