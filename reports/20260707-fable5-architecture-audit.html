壹目標管線(五階段,順序即制度)

ADR-0001。核心洞見:近重複組是 metadata 恢復通道——WeChat/LINE 轉存檔 常是「原檔還在收藏某處」的壓縮版,先去重就不用估日期。所以去重必在補值之前。

貳三大架構風險(診斷)

風險 1|單資料夾工具 vs 批次管線的錯位● 最高

狀態只活在單次 scan 記憶體與單資料夾 .phoxif_log.json。 「這張照片在別台電腦出現過嗎?」「這個估計日期是誰寫的、原值是什麼?」——現有架構答不出來。

修法:SQLite catalog 作為脊椎(ADR-0002,sha256 主鍵、證據欄唯讀、 migration 紀律),GUI 轉為駕駛艙。

風險 2|安全規則紙上嚴格、程式碼違規,違規會繁殖▲ 高

design.md 明令禁止的 -overwrite_original 在 actions.py:190,261,308,329 有 4 處(legacy 另 4 處,全 repo 基線 8); convert.py:167 轉檔後無條件永久刪除原始影片; sorter.py:401 Del 按鈕直接 unlink;_rotate_pillow 原地覆寫無 temp。 AI 開發者會模仿程式碼而非文件——違規模式繁殖。

修法:EXIF 寫入收斂到單一 choke point(ADR-0006:temp → 寫入 → read-back → 原子替換 → log)+ grep 閘門機器看管(quality.md G1/G2)。

風險 3|零測試 + 外部工具假設散落▲ 高

exiftool/ffmpeg 的行為假設散在 5+ 模組,legacy 腳本的 subprocess 無錯誤處理。 改任何 heuristic 都沒有機器訊號告訴你弄壞了什麼。

修法:本次已建 tests/(fixture 動態生成,22 cases 全綠); 之後紀律=改 heuristic 先加 case、先紅後綠。

參錯誤極性不對稱(整套 metadata 決策的底層邏輯)

遇到 ADR 沒覆蓋的新決策,先問:「錯了之後,使用者發現得了嗎?修得回嗎?」

日期 → 盡量填 + 標記

錯=timeline 偏移,有 phoxif:date-estimated keyword 可搜尋、 catalog 可回復。六級信心階梯查表寫入(ADR-0004)。

GPS → 寧缺勿錯

錯=地圖上可信的謊言,會被當成事實。只准人工斷言映射 + 嚴格條件的時間鄰近推斷;轉存檔一律不推斷(ADR-0005)。

刪除 → 不可逆,最嚴

一律 send2trash + 驗證閘;永久刪除是紅線, G2 閘門看管(quality.md §4)。

肆最容易讓 AI 開發者走偏的四個地方

#偏航正確方向(判準)
1先做日期補齊、後做去重(明星功能直覺) 去重先行是產出品質分水嶺;配對到原檔=丟轉存檔,免估日期(ADR-0001)
2估計日期直接寫入、不留標記 不標記=不可逆污染;keyword+catalog 原值是底線(ADR-0004)
3信任跨機器複製後的 mtime 只有 Ingest 當下從來源記錄的 mtime 可用,且是最低信心級
4對轉存檔做時間鄰近 GPS 推斷 轉存檔日期本身是估的,疊加推斷=誤差相乘;禁止(ADR-0005)

伍行動計畫(Phase 0–5,正本在 docs/roadmap.md)

排序依 Metal 定案優先序:①跨電腦收集與去重 ②WeChat/LINE 日期/GPS 補齊。 規模:S=單 session、M=2-3 sessions、L=需拆分。

P0

安全止血 + 驗證地基

規模 S✔ 弱模型自主
修掉會毀資料的程式碼:convert.py 刪片閘、sorter Del 改 trash、 建 exif_writer、actions.py 4 處收斂(TODO P0-1~4)。
最易做錯:改 _rotate_pillow 時弄丟「rotate 後 Orientation 重設為 1」的既有行為——先寫測試鎖住再動。
P1

Catalog + Ingest 收集器

規模 M◆ schema 需 Metal 審核
SQLite schema + migration;掃來源根目錄 → sha256/phash → 記錄證據入庫;冪等重跑。
最易做錯:把 ingest 寫成「移動檔案」——Phase 1 只讀不動, 搬移是 Archive 的事,動了就毀證據。
P2

跨機器去重(exact → near)

規模 M◆ 首批結果需抽查
「哪份贏」規則:EXIF 完整度 > 解析度/大小 > 相機命名勝過轉存命名; 輸家只進垃圾桶 + catalog 標記。首批 dry-run 給 Metal 抽查後才 execute。
最易做錯:把 near-dup 門檻調鬆「多抓一點」——誤殺的是 不可再生的原檔。調整需附誤判抽查數據。
P3

Enrich:日期補齊 → GPS

規模 M✔ 自主(首批抽查)
六級信心階梯 + sanity 檢查 + keyword 標記,寫入走 exif_writer; 開工首件事:抽 30 個真實轉存檔驗證檔名格式假設 + 實測 Immich keyword 可搜尋。
最易做錯:時區。epoch 是 UTC,直接 fromtimestamp() 在旅行照 上會錯 1–16 小時;一律走 config 時區,測試固定 tz 斷言。
P4

Archive + Immich 對接

規模 S-M◆ NAS 寫入動前必問
歸檔到 YYYY/YYYY-MM/ 樹 + sha256 校驗 + 冪等; Immich external library scan(ADR-0003,與既有生產環境對齊,不做 API 上傳)。
最易做錯:重複歸檔成 _1 副本——歸檔前必查 catalog 的 archived_path,冪等是驗收條件不是加分項。
P5

GUI 駕駛艙化

規模 M-L◆ UX 變更需審核
管線五階段裝進既有五步 GUI;批次/來源管理;人工佇列。 端到端 demo:兩來源 → 去重 → 補值 → 歸檔,全程無 CLI。
最易做錯:在 routes.py 重新實作管線邏輯(已有 1039 行前例) ——GUI 只准呼叫管線模組。
